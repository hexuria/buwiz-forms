# What the official program prints past the paper's rows

Research, report only. Official source: `hexuria/buwiz-validation` (byte-exact BIR Offline
eBIRForms package) at commit ea8334a; hash verification in README.md — 35 of 38 pinned form
HTAs match the buwiz-forms pins byte for byte; the 3 mismatches (1601fq, 1603q, 1702q) are not
growable-table forms. Package version: the tree carries Release Notes 7.9.6.1 plus the 7.9.6.2
line added on top (manifests 7.9.6.0/7.9.6.1/7.9.6.2/7.9.6.2.1 all present); per-form pins hold,
so this is the pinned generation. The BIRForms.exe launcher pin (de8ef0815…) cannot be re-checked
here — the launcher exe is not part of the forms tree; the per-form HTA pins are the check that matters.
Sources were read only; nothing was run, submitted, or credentialed.

## The universal mechanism (this changes the shape of the answer)

The official program has **no print code per row at all**. Every form's `printme()`
(file:line per form in the table below) does the same thing: restyle the live DOM
(hide the watermark, set `#formPaper`/`#wrapper`/`#container` to max-width 8.3in,
make every text input read-only and white) and call `window.print()`. Print CSS
(`package/css/print.css`) hides `.printButtonClass` — the buttons, menus, Prev/Next
pager controls — and nothing else. Because the add-row handlers insert new rows
**into the form's own HTML tables in the same document** (e.g. 1601C `addSchedule()`,
BIR-Form1601Cv2018.hta:1316 onclick → function at the script block, zero-based continuous
ids `frm1601c:sched1:txtMonthYear{i}`), rows past the paper are simply part of the
printed document and flow onto however many extra sheets the print engine paginates.

Consequences, uniform across every growable table:

- **What prints past the paper's rows: every row, bare.** Not repeated pages of the
  schedule, not a separate attachment listing — the schedule table itself just keeps
  going down the flow. No row is ever dropped from print; the same rows that are in
  the DOM are in the printout. (Modal tables are the one structural exception, below.)
- **Header on overflow sheets: none.** There is no identity strip, no repeated TIN /
  branch / name / period, no repeated table head, no page numbering generated by the
  application. The overflow sheets carry the bare table rows (and whatever the browser
  chrome adds). The 1707A print alert is explicit that the application expects NO
  chrome either: *"all Margins must be 0.166 and all Headers & Footers must be set to
  empty"* (BIR-Form1707Av2021.hta:3803-3804, same alert in the other legal-size forms).
- **Row numbering: continuous**, because the rows are renumbered in the DOM itself
  when added (the row ordinal is printed text in the row, e.g. `(i+1)` in
  addSchedule — no separate print-time numbering exists).
- **Totals: print in-flow wherever they sit in the table**, after the last row, and
  they include every row because computation runs over the same backing array that
  the rows were built from (e.g. `computeSchedule1()` iterates `schedule1ToCommit`).
  If a print-page break lands mid-table, the total simply appears wherever it falls;
  nothing repaginates it. Nothing is ever printed twice.

The paper's fixed row count is therefore only a *layout* fact in the official program:
the first sheet looks like the paper; past it, the print degrades to a bare flowing
table with no heads and no identity. There is no maximum: no add-row handler in any
form has a row-count cap — the only alerts are incomplete-row guards ("Cannot add row.
There is an empty description on …" BIR-Form1707v2021.hta:3228/3232, same in 1702EX
:8932/8936; "First row cannot be deleted." 2200P:6502, 2200M:6177; per-row validation
alerts in 2200A:7435, 2200M:6321). Verified by reading the handlers: addSchedule
(1601C), addRow_RealProp/addRow_Fam (1801 :5135/:5195), addSchedule1/2/3 (2000
:3397/:3535/:3659), addFieldsForSched1 (2200A :7410, 2200P :6473, 2200M :6148),
ConditionAddRow/AddRow_*PopTable (1707 :2755/:2954, 1702EX :7850/:7987/:8128),
AddrowChecking_ModalTable (1702MX :7997), addRow_schedule1 (1700 :4937),
addlistSched2/3 (2550M :4267/:4793+, 2550Q :4711), AddTaxTransRecord (2552 :2751),
addSchedule1 (2000OT :3257).

## The one structural exception: modal/popup tables print as separate sheets

Forms whose growable tables live in modals print them with `printModal(modalID)`:
the modal is un-hidden, reclassed `modalPrint` (95% width, static position, 1px border
— e.g. BIR-Form1707Av2021.hta:61-69) and printed **on its own sheet, separately from
the main form**. The sheet carries the schedule title and the table's column heads
(e.g. "Schedule 1 / List of Transactions Resulting to Gain", tblModalSched1Header,
BIR-Form1707Av2021.hta:1995-2010) — but **no TIN, no taxpayer name, no period, no page
number**, and rows flow bare past the first page of the modal sheet exactly as in the
universal mechanism. printModal exists in: 1707A :3776, 1707 :6897, 1702EX :14779,
1702MX :22054, 1700 :5240, 1702RT :6447, 2200S :9967, 1601EQ :3856.

## Differences, worst first

1. **Rows the official prints and the engine does not: none found.** The official
   mechanism prints everything in the DOM by construction; the engine's continuation
   pages are built from the same writer-key rows. The risk is inverted: the official
   print is *unstructured* — rows flow with no heads, no identity, and a print-page
   break can land mid-table or even mid-row — while the engine repaginates cleanly.
   So the honest statement is: **the engine deliberately does not match the official
   program here; it is strictly better organized.** Nothing in the official behavior
   is a feature worth copying except one: rows are never lost.
2. **Totals.** Official: the total row prints in-flow immediately after the last row,
   wherever the page break happens to fall; it always includes every row because it
   is computed over the full backing array. Engine: totals are carried onto the final
   continuation page with the official total label, and mid-table breaks print
   "Continued on the next page" (band_flow.rs header comment lines 16-20). Both
   include every row; placement differs by design. No loss either way.
3. **Headers and numbering.** Official overflow sheets have *no* TIN/branch/name/
   period strip, no repeated table heads, no page numbers — the application even
   instructs the filer to empty the print engine's own headers/footers
   (BIR-Form1707Av2021.hta:3803). Modal tables print as separate sheets carrying only
   the schedule title and column heads. The engine adds all of these (page_header with
   TIN & taxpayer name, "Page \<p\> (continued)", repeated table_head marked
   "(continued)"). Row *numbering* matches: both continue the official sequence
   (engine continuation.rs format_row_label incl. lettered ordinals; official
   renumbers in the DOM, e.g. `(i+1)` and LetterIteration in 1707/1702EX).
4. **One behavioral consequence worth noting for the merge decision:** because the
   official overflow print is bare and headless, a third party (or the BIR receiving
   office) cannot reassociate an overflow sheet with its return — the engine's
   identity strip fixes a real defect in the official print, so exact behavioral
   parity is neither possible nor desirable on this axis. What parity requires is
   only: every row prints, totals include every row, numbering is continuous.

## Evidence limits, stated honestly

- "Rows flow bare" is structural fact (the print IS the DOM), not a rendering test —
  the package was never run, per instructions. Print-engine pagination details
  (exactly where breaks land) are IE/HTA-chrome-dependent and unobservable here.
- 2200T/AN/C are outside the report scope (no growable tables in the earlier report).
- The three hash-mismatched forms (1601fq/1603q/1702q) have no growable tables in
  scope; the version question is documented in README.md.
